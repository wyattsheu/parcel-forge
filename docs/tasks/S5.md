## Goal
Given a failing case, an agent reads the structured findings, proposes a bounded
repair to the **specification or the generator**, and the pipeline re-runs. It fixes
at least two fault classes and, just as importantly, **stops correctly** when it cannot.

## Binding design rules (these are not negotiable, see D012)

1. **Deterministic checks own pass/fail.** A model-based critic may only
   (a) propose a repair or (b) downgrade a deterministic pass to "needs human review".
   It can never turn a fail into a pass. Rationale: Articulate-Anything reports its
   critic's dominant error is the false positive — declaring an incorrect result
   correct on "difficult-to-notice errors". With this rule, a wrong critic costs a
   wasted iteration, never a wrong verdict.
2. **The actor edits the spec or the generator, never the USD output.** Editing the
   artifact directly produces a fix that cannot be replayed or explained.
3. **Minimal diffs.** LL3M reports that refinement agents rewrite whole scripts when
   they lack shared context. Every repair is recorded as a patch against the previous
   spec, and a repair that rewrites more than it needs to is itself a finding.
4. **Two separate checks, two separate records:** *was the change applied?* and
   *did the change fix the problem?* LL3M's verification agent exists because these
   are different questions and conflating them hides no-op "fixes".
5. **Forbidden repairs, enforced by an allowlist, not by good intentions:** the agent
   may not touch `profiles/`, `tests/`, `src/parcel_forge/validation/`, or any
   tolerance. Repairing the thermometer is not repairing the room.
6. **At most three attempts**, with the stopping reason recorded: fixed, budget
   exhausted, or out of scope.

## Acceptance
- At least two fault classes repaired, each with before/after runs, the patch, and the
  new test results.
- At least one case where the agent correctly **refuses** and stops with a reason.
- A regression test proving the allowlist blocks a patch that touches a profile or a
  validator, even when that patch would make the case pass.

## User learning
Concept: the dangerous failure is not "the robot broke it", it is "the checker said
it was fine". That is why the model never gets to say pass.
Experiment: hand the loop a case whose only problem is a too-thick wall, and watch it
change `wall_thickness_m` rather than the tolerance. Then hand it a case that cannot
be fixed by any spec change, and confirm it stops instead of inventing one.
