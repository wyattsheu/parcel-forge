## Mass properties (S4, first half)
`src/parcel_forge/mass_properties.py`, pure maths, no simulator. Reproduces every
value in handbook section 19 to 10 decimal places:

| quantity | value |
| --- | --- |
| plate volume | 0.0010105000 m^3 |
| bottom mass | 0.0593765463 kg |
| each x wall | 0.0286986640 kg |
| each y wall | 0.0416130628 kg |
| COM z | 0.0552337952 m |
| Ixx / Iyy / Izz | 0.0016619320 / 0.0027588147 / 0.0034580587 kg m^2 |

Density is taken over plate volume, never the outer envelope; a test pins that the
two differ by ~8.9x. Adopted from Scalable Real2Sim: confidence tiers on every
quantity (nothing is `measured`), and the pseudo-inertia feasibility check
(positive definite plus the triangle inequalities), with tests proving it rejects
an impossible tensor and accepts the boundary case.

## The drag problem: not our bug
Cause found in `omni/physxui/scripts/input.py`: physics grab/push input actions are
registered only on a timeline PLAY event and removed on STOP/PAUSE. The user's
viewer drives physics by calling `get_physx_simulation_interface().simulate()`
directly and never plays the timeline, so mouse interaction can never arm. Our probe
is an ordinary dynamic rigid body; nothing about it was wrong.

Their script belongs to another project and was not modified. Instead `pf view`
was added: it plays the timeline (arming interaction) and holds the probe kinematic
for a configurable period so the drop happens after a human has connected, which
also answers D019. It refuses to start if the WebRTC ports are busy and prints the
owner's own stop command rather than killing anything.
